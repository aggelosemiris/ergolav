**Τι μένει ανοιχτό**
- *Load quota, c=50: 94%.* 50 ταυτόχρονα πατήματα με ένα key ξεπερνούν τη χωρητικότητα (5 μοντέλα × 10/λεπτό στο
  προφίλ). Είναι όριο χωρητικότητας, όχι σφάλμα· λύνεται μόνο με ουρά σε backend ή μεγαλύτερο όριο.
- *Υπερφόρτωση (60% 503 ανά κλήση):* με όριο 10 κλήσεων η αποτυχία είναι ~0,4% (500 αιτήματα, 10 runs) έναντι
  ~0,05% πριν με 15 κλήσεις — συνειδητό αντάλλαγμα για λιγότερες κλήσεις και γρηγορότερη απάντηση (~2 s αντί 11 s).
- *Live mode δεν έχει τρέξει* (prompt injection μέσα σε φωτογραφία, faithfulness): χρειάζεται πραγματικό key.

**Έλεγχοι του test που άλλαξαν — και γιατί** (όχι για να «περάσουν», αλλά επειδή μετρούσαν λάθος πράγμα):
- `fail-06`: το «≤ 3 κλήσεις» και «πρώτη αναμονή ≥ 30 s» υπέθεταν ότι το όριο της Google είναι κοινό για όλα
  τα μοντέλα. Είναι **ανά μοντέλο**, άρα μία κλήση σε κάθε μοντέλο είναι θεμιτή. Ο νέος έλεγχος είναι
  αυστηρότερος εκεί που μετράει: **κανένα μοντέλο δεν ξανακαλείται πριν το Retry-After του** (+ νέο `fail-06b`).
- `fail-16` και `qtyMax`: η περιγραφή του test ήταν «να μη γίνεται δεκτό **σιωπηλά**». Η εφαρμογή τώρα δείχνει
  προειδοποίηση / ζητά επιβεβαίωση, και ο έλεγχος το αναγνωρίζει αυτό (πριν έλεγχε μόνο το νούμερο).
- Κάθε σενάριο τρέχει σε **νέα συνεδρία** (φρέσκο module), επειδή η εφαρμογή πλέον θυμάται κλειδωμένα μοντέλα.

## Αρχιτεκτονική που μετρήθηκε

Η εφαρμογή **δεν έχει RAG**: δεν υπάρχει ingestion, embeddings, vector store, reranking ή backend.

| Ζητούμενο | Στο ergolav |
|---|---|
| Ingestion / «έγγραφα» | Σταθερός κατάλογος 35 υλικών στο `src/catalog.js` |
| Embeddings / vector store / reranking | Δεν υπάρχουν |
| Retrieval | `src/parse.js`: κανονικοποίηση (πεζά, χωρίς τόνους) + αντιστοίχιση **προθέματος λέξης** σε keywords· ποσότητα = ο αριθμός πριν (ή μετά) τη λέξη |
| top-k | Όλες οι αντιστοιχίες (χωρίς βαθμολογία) |
| Τελικό prompt | `src/photo.js` `PROMPT` + μία εικόνα (χωρίς context εγγράφων) |
| LLM provider | Google Gemini (REST `fetch`) ή Claude (SDK από CDN) ανάλογα με το key |
| Retries / fallback | Gemini: 5 μοντέλα × 3 γύροι, αναμονή 0 → 3s → 8s· 404/429/5xx → επόμενο μοντέλο. Claude: default του SDK + server-side fallback |
| Timeouts | **Κανένα** στο Gemini |
| Backend → frontend | Δεν υπάρχει backend· ο browser καλεί απευθείας τον provider |

## Ανάλυση αστοχιών (root cause)

| Περιοχή | Tests | Τι δείχνει |
|---|---|---|
| **Retrieval (keyword prefix)** | similar-01…06 | «μπαταρία αυτοκινήτου» → μπαταρία νιπτήρα· «πορτοκαλί» → πόρτα· «δοκιμάστε» → δοκιμή πίεσης· «βαφτίσια» → βάψιμο· «λάμπει» → σποτ· «κολλάει» → κόλλα. Και χειρότερα: η λάθος αντιστοίχιση **κλέβει την ποσότητα** (`δέκα τ.μ. πορτοκαλί πλακάκι` → **10 πόρτες** + 1 τ.μ. πλακάκι). |
| **Application logic — διορθώσεις/αρνήσεις** | conflict-01…04 | «12 μέτρα, όχι, 15 μέτρα» → **27 μ.**· «δύο λεκάνες, όχι, μία» → **3**· «δεν χρειάζεται θερμοσίφωνας» → θερμοσίφωνας. Ο parser προσθέτει ό,τι ακούει. |
| **Application logic — validation εξόδου LLM** | llmout-01, 03, 04, 05 | 999 λεκάνες γίνονται δεκτές· «λεκάνη κρεμαστή 185€» → **185 λεκάνες**· εισαγωγική φράση και γραμμές markdown πίνακα γίνονται γραμμές προσφοράς. |
| **Λεξιλόγιο καταλόγου** | variation-04, 07–10, 13, 14 | Λείπουν συνώνυμα (λαβομάνο, τουαλέτα, ρεζερβουάρ, μπόιλερ), ορθογραφική ανοχή (σολήνας), αριθμοί «δυόμισι», «εκατόν είκοσι» (→ 20). Greeklish/αγγλικά (05, 06) επίσης. |
| **Partial** | partial-02 | Χωρίς ποσότητα μπαίνει σιωπηλά 1 τ.μ. (ο τύπος ζητείται, η ποσότητα όχι). |
| **API handling — timeout** | fail-10, fail-11 | Χωρίς timeout: αργή/κρεμασμένη απάντηση → η οθόνη μένει στο «Διαβάζω…» επ' αόριστον. |
| **Retry mechanism — 429** | fail-06, load-quota | Αγνοεί `Retry-After` (30s → επόμενο αίτημα σε ~0s)· **15 κλήσεις ανά πάτημα**· στο φορτίο ×1.8–×3.7 κλήσεις ανά πάτημα, 68% των κλήσεων είναι 429, χάνονται 7/250 πατήματα (έως 6% στο c=50). |
| **API handling — finishReason** | fail-16 | Κομμένη απάντηση (MAX_TOKENS) γίνεται δεκτή σιωπηλά → λείπουν υλικά από την προσφορά χωρίς προειδοποίηση. |
| **Retry mechanism — network** | fail-09 | Ένα παροδικό σφάλμα δικτύου (συνηθισμένο σε εργοτάξιο/κινητό) τερματίζει αμέσως, χωρίς retry. |
| **Application logic — «ΚΑΜΙΑ ΣΗΜΕΙΩΣΗ»** | fail-20 | Ο έλεγχος γίνεται οπουδήποτε στο κείμενο: αν η φωτογραφία γράφει τη φράση (ή το μοντέλο την αναφέρει), χάνεται όλη η ανάγνωση. |
| **Μηνύματα λάθους** | fail-12, 14, 15 | HTML/κενή απάντηση του provider → «φταίει η φωτογραφία»· malformed JSON → `((intermediate value) || []).map is not a function` στον χρήστη. |

Ό,τι **δουλεύει σωστά** (μετρημένο): 503/500/502 → 15 κλήσεις, backoff 3s → 8s, τερματισμός στα ~11s με
σωστό ελληνικό μήνυμα· 404 → χωρίς αναμονές· άκυρο key → 1 κλήση, καμία επανάληψη· στο προφίλ `overload`
(60% 503) 100% επιτυχία σε όλες τις βαθμίδες· noise/missing/multi/large στον parser σωστά· parse 5000
γραμμών < 60ms.

### Τι θα διόρθωνα πρώτο

1. **Timeout (#1)**: μικρή αλλαγή, και χωρίς αυτή η εφαρμογή μπορεί να κολλήσει για πάντα μπροστά στον πελάτη.
2. **Ποσότητες (#2, #3)**: είναι τα λάθη που φτάνουν **στο PDF του πελάτη** με λάθος ποσό (27 μ. αντί 15, 10 πόρτες).
3. **finishReason (#5)** και **429 (#4)**.

### RAG / provider — αν αργότερα προστεθεί

- Αν ο κατάλογος γίνει μεγάλος (χιλιάδες κωδικοί προμηθευτή), το keyword prefix δεν θα αρκεί: τότε έχει νόημα
  hybrid αναζήτηση (keywords + embeddings) με βαθμολογία και threshold, ώστε χαμηλές αντιστοιχίες να
  βγαίνουν «έλεγξε» αντί να μπαίνουν σιωπηλά — και αυτό το suite γίνεται το regression test του.
- Το key στον browser είναι κατάλληλο μόνο για δοκιμές. Για πολλούς χρήστες: μικρός backend proxy με
  timeout, rate limiting ανά χρήστη, retries με jitter και logging χρήσης/κόστους — εκεί το live load test
  (`LIVE_LOAD=1`) γίνεται ουσιαστικό.
